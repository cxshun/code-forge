# 第 3 篇 · 接上 IM 才是真地狱：当你的 Agent 搬进飞书群

> 本篇是专栏样稿。系列大纲见 `outline.md`，文中 D 编号引用自项目的决策索引
> `decisions.md`。代码均来自开源仓库 code-forge 的真实切片。

前两篇里，我们的 Agent 一直住在终端里：一个 while 循环，接上工具，读文件、改代码，
跑得像个模范员工。很多教学系列到这里就结束了。但这篇想讲的是我把 agent 搬进飞书
群的那个下午——**我意识到，终端是 agent 最温柔的宿主，IM 是最苛刻的那个。**

Web chat UI 看起来朴素，其实你享受着一整套 Web 技术的红利：SSE/WebSocket 推流、
前端 markdown 渲染器帮你处理流式分片、typing indicator 告诉用户"对方正在输入"。
而 IM 什么都没给你：消息限频、事件重推、群聊里谁说话都要你自己判断，甚至"正在
处理中"这个状态，你都得自己发明表达方式。

这篇按接入层真实的数据流走一遍：**触发 → 去重 → 路由 → 反馈 → 渲染**，五个环节
里埋着五个坑。

## 一、长连接还是 Webhook：第一个架构分叉

飞书的事件接入有两种方式：webhook 回调和 WebSocket 长连接。

Webhook 意味着你的服务必须有公网地址、固定回调 URL、证书，而且每加一个飞书 App
都要去开放平台改一次配置。对多租户产品（我们的 D2/D7：支持配置多个企业自建应用）
来说，每个租户注册自己的 App，还要挨个填回调地址，运维成本线性增长。

WebSocket 长连接把方向反了过来：**服务主动连飞书，事件从连接上推下来**。没有公网
暴露面，没有回调配置，加一个 App 就是加一条连接。代价是你要自己管理连接的生命
周期——这个决定后来在第 8 篇会给出最惨痛的回报（lark SDK 的模块级事件循环竞态，
两个 App 互相打崩），但架构上它仍然是对的：**连接受控在你手里，好过公网暴露面
失控在别人手里。**

事件从连接上下来之后，第一件事不是处理，是**转发**。lark SDK 的回调跑在连接线程
的事件循环上，而我们的数据库连接池、Redis、Run 队列全部活在 FastAPI 的业务事件
循环里。跨线程转发协程用的是 `asyncio.run_coroutine_threadsafe`：

```python
# app/feishu/ws_pool.py（简化）
fut = asyncio.run_coroutine_threadsafe(
    self._handler(event_dict, app_id, app_secret),
    self._business_loop,   # FastAPI 的业务 loop
)
fut.add_done_callback(_on_future_done)  # 异常不被静默吞掉
```

这里有个容易忽略的细节：`add_done_callback` 不是装饰品。跨线程转发后如果 handler
炸了，异常只会躺在 future 里没人看见——你的 agent 会"安静地"不理人，而不是报错。
接入层的每一个环节都要回答同一个问题：**它失败的时候，用户看到的是什么？**

## 二、触发规则：群聊里谁有资格唤醒 Agent

消息进来，先过 `parse_message_event` 拆出结构化上下文：发送者、纯文本（剥掉
`<at>` 标签）、是否 @了机器人、消息类型、被引用消息的 id。

然后是触发规则。我们的规则简单到可以贴在墙上（D13/D21）：

- **群聊：必须 @ 机器人才触发**；
- **私聊（p2p）：直接触发**；
- 其他类型：忽略。

"群聊必须 @"不只是产品选择，是生存需要——一个在群里自嗨的 agent 会把每个技术
方案讨论都当成对自己的提问，token 账单和群友的耐心会同时爆炸。至于权限模型
（谁能用、用哪个工作空间），MVP 我们主动砍掉了：**拉群即用**。写清楚你不做什么，
比写清楚你做什么更难，但更值钱。

## 三、去重：飞书会重发同一条消息

接下来这个坑，没接过 IM 的人基本不会想到：**飞书会重推事件。**

长连接断线重连后，服务端会补推窗口期内的事件；某些边界情况下同一条消息也会推
两次。没有去重的话，一条"帮我修个 bug"会唤醒两个 agent 实例，在同一个工作空间
里打架。

去重方案是教科书级的 SETNX + TTL（D38），但值得看的是参数选择：

```python
# app/feishu/dedup.py
DEDUP_PREFIX = "msg_dedup:"
DEDUP_TTL_SECONDS = 600  # 10 min

async def acquire(backend, message_id: str) -> bool:
    return await backend.set(
        f"{DEDUP_PREFIX}{message_id}", "1", nx=True, ex=DEDUP_TTL_SECONDS
    )
```

去重键必须**在进 Run 队列之前**判定——排队也是消费，等队列里去重就晚了。TTL 给
10 分钟：短了挡不住重连补推的窗口，长了纯属占内存。这个函数只有 5 行，但它挡住
的是最难复现的那类 bug——**你在开发环境永远收不到重推，它只在生产网络的抖动里
出现。**

## 四、反馈：IM 里没有 typing indicator，但有表情

Agent 排队、思考、跑工具，可能要几十秒到几分钟。这段时间用户盯着群里的沉默，
多半会再 @ 一次（然后触发第二个 Run……去重键拦不住它，因为是新消息）。

Web 产品的答案是 typing indicator，IM 机器人没有这个 luxury。我们的替代方案是
**在用户那条消息上打一个表情回应**：

```python
# app/feishu/handler.py（简化）
reaction_id = await client.add_reaction(ctx.message_id, "OnIt")  # 收到 ✌
# ... Run 结束后
await client.delete_reaction(ctx.message_id, reaction_id)        # 撤掉，卡片接管
```

一条消息贴上"OnIt"，等于告诉全群：这条已受理，正在处理，别催。处理完表情消失，
回复卡片出现——**用 IM 的原生语言，模拟了 Web 产品的交互语义**。这个模式不是我们
发明的（Slack 上的 bot 早就在用 emoji reaction 做受理回执），但它验证了一个
接入层的设计原则：**别把 Web 的交互硬翻译成 IM，去找 IM 自己的表达方式。**

## 五、引用回复：上下文 ≠ 历史

用户在群里引用机器人上一条回复，补一句"第二种方案展开说说"。这是引用的直觉
语义：**延续刚才那个话题**。

第一直觉是恢复被引用消息对应的那个 session，把历史对话装回上下文。我们明确
拒绝了这个方案（D39）：session 可能已经过期被清理，历史可能很长，而且"引用"
在 IM 里的真实语义经常只是"我说的这个跟那条有关"，不是"接着那条聊"。

最终方案出奇地朴素：**把被引用消息的正文拉下来，作为纯文本前缀注入**：

```python
# app/feishu/handler.py（简化）
quote = await fetch_quote_text(client, ctx.parent_id)
user_message = f"{quote}\n{ctx.text}" if quote else ctx.text
```

被引用的内容被降维成一段"参考资料"，而不是对话历史。配套规则：**引用 + @ 才
触发，只引用不 @ 不触发**——和群聊的总体触发规则保持一致。

这个设计后来还派生出一个小坑：被引用的消息本身可能是**机器人发的卡片**。从卡片
JSON 里提取纯文本要兼容新旧两种卡片结构（新版 `header.title` 是 dict，旧版顶层
`title` 是字符串），这正是 commit `ebbeb6e` 修的东西——接入层最不缺的就是这种
"边界之外还有边界"。

## 六、踩坑重头戏：流式渲染的溃败与回退

现在说这篇最大的坑。前三篇我们建立了流式信仰：LLM 的 token 是流出来的，UI 就该
流式渲染，用户盯着字一个个蹦出来，体感延迟趋近于零。Web 版这么做天经地义。

第一版飞书卡片也这么做了：`on_text` 回调里累积文本，节流地 `update_card`——比如
每秒最多更新两次，把流式分片刷到卡片上。看起来很美。

然后有用户让 agent 输出一张**GFM 表格**。

问题来了：流式分片不认识 markdown。表格渲染到一半，卡片上是一行残缺的
`| 模块 | 状态 |`，下一次节流刷新补全了表格，再下一次又可能把它截断在代码块
中间。Web 前端的 markdown 渲染器会在每次重渲染时把完整文本重新 parse 一遍，
分片对它只是"内容变多了"；而飞书卡片要么用有限的 markdown 支持，要么自己维护
一个**流式安全的渲染器**——你要在分片的任意位置，判断"此刻这段文本处于一个完整
的结构里，还是一个半截结构里"。

我们试过给渲染器打补丁，最后选择了诚实的回退。现在的卡片生命周期是这样的：

```python
# app/feishu/handler.py
async def on_text(self, delta: str) -> None:
    self._full.append(delta)        # 只累积，不渲染

async def on_tool_call(self, _tc: dict) -> None:
    self._full.clear()              # 工具调用 = 前面的文本是中间过程，弃

async def on_done(self, exc) -> None:
    full = "".join(self._full)      # 完成后一次性渲染
    await self._update(full[:_CARD_TEXT_CAP])  # 6000 字上限
```

三个决定值得逐个说：

1. **`on_text` 只累积不渲染**。流式的体感收益，被"表格残缺闪烁"的观感损失完爆。
   IM 用户对"稍等后出完整答案"的容忍度，远高于对"残缺表格来回跳"的容忍度。
2. **`on_tool_call` 清空累积**。这个很容易漏：agent 回答前通常会先"我来看一下
   xx 文件"，这些中间文本如果不清空，最后会跟真正的答案拼在一起。**中间过程和
   最终回复的边界，不是文本流里自带的，是工具调用事件给的。**
3. **渲染是一次性的，但不是裸的**。`on_done` 里那个"完整正文"要经过自研的
   GFM→卡片元素渲染器：表格 parse 成结构化 elements、代码段先圈出来保护起来
   防止被误格式化、6000 字截断防飞书接口限制。一次性渲染不是降低要求，是把
   复杂度从"流式安全的渲染"集中到"一次性的完整渲染"。

这次回退教会我的是：**流式不是信仰，是权衡。** Web 场景下流式的收益（体感延迟）
远大于成本（前端渲染器现成）；IM 卡片场景下成本陡增（自己写流式安全渲染器），
收益却没有变大——群聊用户本来就不是盯着屏幕等字蹦的。同一套产品逻辑换个宿主，
最优解可能完全相反。

## 七、静默失败：接入层最阴的 bug 形态

最后一个坑不讲技术讲形态。commit `4d4f579` 修的 bug：私聊用户第一次发消息时，
需要自动把会话绑定到一个工作空间（p2p 自动建专属 WS）。功能上线后偶发"机器人
不理人"——没有异常日志，没有报错卡片，一切看起来都在正常运转，只是消息进了
黑洞。

排查发现是绑定链路上有一个分支返回了 None，而调用方对 None 的处理是"忽略这条
消息"。每一层都"正确"地处理了自己的返回值，组合起来就是静默失败。修复本身很
小，但我从此给接入层立了条规矩：**每条路径的终点，要么是用户可见的反馈，要么是
一条带上下文的日志，二选一，不许有第三种结局。** 现在回头看 `handler.py`，几乎
每个 if 分支都跟着一行 `log.info("unbound chat, ignore: ...")`——这些日志平时
是噪音，出事时是唯一线索。

## 小结

接入层的全部工作，可以压缩成一句话：**Agent 的智能在模型里，但 Agent 的可靠性
在这些五行的防御性代码里。** 去重是五行，表情回执是十行，分支日志是一行一行
加上去的——单独看每一行都不值得写进简历，少了任何一行，生产事故就会替你补上
这一课。

下一篇我们处理接入层交出来的东西：三个同事同时 @机器人，Run 队列怎么排队、
怎么取消、怎么在进程被 kill -9 之后假装什么都没发生地醒来。
