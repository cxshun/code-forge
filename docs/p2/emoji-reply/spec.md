# P2 - Emoji 确认回复：需求规格

> 二期迭代。一期 MVP 文档见 [../../mvp/spec.md](../../mvp/spec.md)。

---

## 1. 背景与目标

### 1.1 问题

MVP 已实现"思考中"进度卡片（F3.1.5 / T4.5）作为即时反馈，但卡片发送本身有网络 RTT + 飞书卡片渲染延迟（~300-800ms）。在 Agent 启动排队 / LLM 首字节延迟期间，用户仍可能感到"消息石沉大海"。

### 1.2 目标

在用户消息上**立即打一个 emoji 表情回应**（飞书 Reaction），作为"已收到"的视觉确认：

- 反应延迟 < 200ms（飞书 Reaction API 轻量，不经过卡片渲染管线）
- Run 完成后自动移除表情（避免视觉残留）
- 与现有"思考中"进度卡片互补：表情 = 即时 ack，卡片 = 持续进度

### 1.3 非目标

- 不替换现有的进度卡片机制
- 不支持自定义表情（MVP 固定使用 `OnIt`）
- 不对私聊场景生效（MVP 仅群聊）

---

## 2. 功能性需求

- **F2.1** 收到用户消息后，在用户消息上添加 `OnIt` 表情回应（飞书 Reaction API）
- **F2.2** 表情添加在 Run 入队之前执行，确保最低延迟
- **F2.3** Run 完成（成功 / 失败 / 中断）后自动移除表情
- **F2.4** 若 LLM 未配置（不入队），也在发错误卡后移除表情
- **F2.5** 表情添加 / 移除失败不影响主流程（best-effort，log warning 不中断）
- **F2.6** 表情移除需持有 `reaction_id`（添加时返回），移除时按 `message_id + reaction_id` 调用删除 API

---

## 3. 非功能性需求

- **NF2.1** 表情操作不阻塞 Run 提交（失败即降级，不重试）
- **NF2.2** 表情添加 / 移除的异常不污染 Run 状态 / Trace 数据
- **NF2.3** 移除操作在 `on_done` 回调中执行，与 Run 生命周期绑定

---

## 4. 约束与假设

- 飞书 Reaction API 要求机器人有 `im:message.reaction:write` 权限
- 机器人需为群成员才能给群消息添加表情
- `OnIt` 是飞书内置表情类型，无需自定义
- 假设 Reaction API 响应时间 < 500ms（实测通常 < 200ms）

---

## 5. 与 MVP 的关系

| MVP 机制 | P2 补充 | 关系 |
|---|---|---|
| F3.1.5 思考中进度卡片（T4.5） | F2.1 OnIt 表情回应 | 互补：表情 = 即时 ack（< 200ms），卡片 = 持续进度展示 |
| F3.3.4 排队反馈卡片 | — | 不变，排队卡片仍由 `on_queue` 回调发送 |
| F3.3.5 Run 完成 on_done 回调 | F2.3 表情移除 | 扩展 `on_done` 回调，在原有清理逻辑后追加表情移除 |

> P2 不修改 MVP 的任何既有逻辑，仅在 `handle_message` 入口和 `on_done` 回调处追加表情操作。
